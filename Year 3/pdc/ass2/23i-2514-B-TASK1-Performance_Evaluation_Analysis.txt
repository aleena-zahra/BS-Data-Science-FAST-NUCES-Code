1. PARALLEL LIFE CYCLE DESIGN

PHASE 1 – PROBLEM UNDERSTANDING
Expensive Computation Tasks Identified:

(a) Tokenisation & Stop Word Removal
    Scans through all words in all documents (40,000 to 70,000 reviews each).
    Total words processed = 400,000 to 700,000.
    Documents are independent; hence, parallel.

(b) Document Frequency Computation (IDF)
    Involves iterating through all documents.
    Each document is independent; hence, parallel.

(c) TF-IDF Computation
    Involves one floating point division and one multiplication for each unique term for each document.
    This computation is data parallel.

(d) K-Means Clustering
    Assignment Step: Computation of distance from K centroids for all N documents.
    Each document involves computation of N*K*FEAT multiplications.
    Re-computation Step: N additions for each of FEAT features.
    This computation is embarrassingly parallel, except for a small serial step.

(e) Cosine Similarity Search
    Involves iterating through all 100 pairs for each of the TF-IDF vectors.
    Each pair is independent; hence, parallel.

    Another task that may be included in the list of tasks to be executed in parallel:
      Vocabulary/inverted index construction. A word -> document_list mapping would facilitate parallel phrase search and relevance ranking.
      Each thread would create a local index, and they would be combined at the end.

PHASE 2 – DECOMPOSITION STRATEGY
  Decomposition strategy chosen:
    DATA DECOMPOSITION (horizontal partitioning)

  The set of documents in the array of size N would be divided into contiguous segments of size approximately N/T.
  Each thread would be allocated a segment of the array to process independently.

  The segments to be processed by each thread would be:
      start_i = i * (N/T) + min(i, N%T)
      end_i = start_i + N/T + (i < N%T ? 1 : 0)

  This would ensure perfect balancing even when N % T ≠ 0.

  The K-Means centroid arrays of size K * FEAT would be replicated for the threads, 
  read-only for each thread during assignment and written locally for each thread
  during accumulation.

PHASE 3 – ASSIGNMENT STRATEGY

  Number of threads selected:
  - Thread version: hardware_concurrency() capped at most 8 
    (an empirical optimum on quad/octa-core machines).
  - OpenMP version: value returned by omp_get_max_threads(), equal to hardware value.
  Worker tasks:
    - Phase 1: Each thread processes docs[start..end], contributing to thread-local data structure localFreq[tid].
    - Phase 2: Each thread computes tfidf[start..end] using shared but immutable global IDF data structure.
    - Phase 3a: Each thread computes cluster[start..end].
    - Phase 3b: Each thread computes localSum[tid][k][f] and localCnt[tid][k].
    - Phase 4: Each thread computes simScores[start..end].

PHASE 4 – ORCHESTRATION STRATEGY

  Merging local results:
    - After each parallel phase, we merge thread-local data in O(V) or O(K*FEAT) iterations in the main thread:
          globalFreq[w] = Σ_t localFreq[t][w]
          newC[k][f] = Σ_t localSum[t][k][f]
          cnt[k] = Σ_t localCnt[t][k]
    - The cost of this operation is negligible because we're merging O(V) or O(K*FEAT) data structures, much smaller than O(N).

  Centroid update strategy for K-MEANS:
  - 1. Broadcast current centroids: no need to lock data structure because it's shared read-only access.
  - 2. Each thread computes partial sums in thread-local data structure: partialSum[k][f].
  - 3. Main thread sums partial sums: newC[k][f] = Σ_t partialSum[k][f]
  - 4. Main thread updates cnt[k] = Σ_t localCnt[k]
  - 5. Main thread updates globalFreq[w] = Σ_t localFreq[w]

PHASE 5 – COMMUNICATION STRATEGY

  Shared variables and access mechanisms:

  Variable              Access Pattern          Protection used
  .....................................................................................................................
  docs[]                Read-only               None needed
  docTF_raw[i]          One writer per index i  Partition-based
                               (by range assignment)   (no lock)
  docTokens[i]          One writer per index i  Partition-based
  tfidf[i]                    One writer per index i  Partition-based
  X[i][]                      One writer per index i  Partition-based
  cluster[i]                One writer per index i  Partition-based
  localFreq[tid]         Fully thread-private    None needed
  localSum[tid][][]     Fully thread-private    None needed
  localCnt[tid][]         Fully thread-private    None needed
  globalFreq             Written only serially   Serial section
  idf                          Written only serially   Serial section
  centroids[][]         Read parallel / write      Serial section
                               serially after join
  simScores[i]          One writer per index i  Partition-based


OpenMP critical sections used:
    #pragma omp critical is used to protect the parallel merge of
    thread-local frequency maps into globalFreq in the frequency counting step.

Race Conditions and Prevention:
    (1) globalFreq accumulation: 
      This is a potential race condition since multiple threads are updating the same word key in globalFreq. 
      This is prevented by merging the parallel computation of frequency maps into globalFreq in a serial fashion.

    (2) docTF_raw[i] write: 
      This is a potential race condition since two or more threads might be updating the same index in docTF_raw. 
      his is prevented by strict range partitioning, i.e., every index is associated with exactly one chunk.

    (3) K-Means centroid write: 
      This is a potential race condition since multiple threads are updating shared centroid arrays. 
      This is prevented by merging the parallel computation of centroid arrays in a serial fashion.

    (4) Cosine similarity results: 
     The computation of simScores[i] is performed by the owner of index i. 
     Hence, there is no race since no two threads share the computation.

3. ANALYSIS AND DISCUSSION

  Sequential baseline:
  All phases of the pipeline are executed on a single core. 
  The cost model is dominated by the K-Means inner loop 
  (cost scales as N x K x FEAT per iteration), 
  followed by tokenization.
  
  std::thread version:
    The work is divided into T equal-sized pieces before threads are launched. 
    The cost of launching threads is paid once for each phase. 
    No synchronization is used in the inner loops, as they are computationally expensive. 
    The speedup is modest, limited by the number of physical cores. 
    The dataset size being small means the work per thread is small
    So parallelism only partially offsets the thread overhead
    
    
  OpenMP version:
    This version uses a thread pool, so the cost of launching threads for each phase is eliminated. 
    This version also includes a form of dynamic scheduling (chunk size 256), 
    which helps improve performance as the length of each review can vary (per-document cost).
    But in this implementation the overhead costs increases the computation time a lot, so much that it takes longer than sequential version.
    
  Scalability:
    Both parallel versions dont scale well for the tokenisation
    This is because the thread overhead is more than the benefit due to parallelism
    As the document is too small with a tiny vocab
    TF-IDF, and similarity phases are embarrassingly parallel
    K-Means scales somewhat less due to the serial centroid
    merge, but since K×FEAT (5×100 = 500 values) < number of docs this
    serial fraction is negligible (Amdahl fraction < 0.1%).

  Bottlenecks:
    - The vocab is 21 words this means that k means and tf idf calculations are low cost (sparse vectors/matrices)
    - The workload is memory light and insuffiecent computation for parallelism to overcome thread cost in the case of openMP
    - Memory bandwidth: There are a lot of documents which consume memory. 
    - Cache pressure may limit linear scaling beyond 4 threads.
